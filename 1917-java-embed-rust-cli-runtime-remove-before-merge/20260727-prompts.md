## 3. Lessons from PyTorch/DJL

DJL's `Platform.java` and native loading approach offers two relevant lessons:

**Lesson 1: Properties-file-driven platform matching.** DJL scans the classpath for `native/lib/<engine>.properties` files to discover which platform binaries are available, then matches against the running system. The plan's `copilot-runtime.properties` with `placeholder=true` already mirrors this pattern (good). DJL's additional nuance: when *multiple* platform JARs are on the classpath (uber-jar scenario), it sorts candidates and picks the best match. The plan's `NativeRuntimeLoader` should handle this case — in the `copilot-native-all` uber-JAR, all 8 `native/<classifier>/runtime.node` resources exist on the classpath simultaneously. The loader must filter by the detected classifier, not just grab the first `runtime.node` it finds.

**Lesson 2: DJL uses `ServiceLoader` for engine discovery but *not* for native library loading.** The plan's decision to use direct instantiation (not `ServiceLoader`) for `NativeBinding` is validated by DJL's architecture: `ServiceLoader` is for user-selectable engine choice; native library loading is deterministic platform detection. This confirms the plan is correct.

**No other DJL lessons apply.** DJL uses JNI (custom C++ JNI bridge compiled per-platform), not JNA. Their loading/extraction is heavily GPU-flavor-aware (cu121, cu118, cpu, etc.) which adds complexity we don't need. Their security fix in PR #3826 (6 months ago) addressed path traversal in extraction — worth verifying our temp-file-plus-atomic-rename pattern doesn't have the same issue (it doesn't, since we control both the resource path and the cache directory structure, and never use untrusted input in path construction).
