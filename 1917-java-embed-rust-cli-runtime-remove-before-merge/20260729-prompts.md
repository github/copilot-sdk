**What The System Does**

This is a backlog-generation stage for the larger `shepherd-task` automation. It converts an implementation plan into an ordered set of detailed GitHub child issues that can later be assigned to Copilot Coding Agent one at a time.

The scripts do **not** create issues. They are interactive prompt generators:

1. Ask for twelve values covering the repository, topic branch, parent issue, plan location and headings, exemplar issues, remote, child issue type, artifacts, and checkbox behavior.
2. Supply defaults for:
   - `BASE_REMOTE`: `upstream`
   - `ISSUE_TYPE`: `Task`
   - `SUPPORTING_ARTIFACTS`: the plan directory
   - `UPDATE_PLAN_CHECKBOXES`: `false`
3. Write an ordinary Markdown file in the current directory named:
   `YYYYMMDD-HHMM-invoke-shepherd-task-create-issues-from-plan-skill.md`
4. Tell the user to paste it into Copilot Chat or pipe it into `copilot --yolo`.

The generated file simply says:

```markdown
Invoke skill `shepherd-task-create-issues-from-plan` with these inputs:
...
```

Thus, execution depends on the skill being installed and discoverable by Copilot. `--yolo` allows the resulting Copilot session to execute GitHub and local commands without interactive approval.

**How The Skill Executes**

The skill in SKILL.md instructs the model to perform this agentic workflow:

1. **Validate**
   - Reject `main` and the repository default branch.
   - Confirm the topic branch exists.
   - Confirm the parent issue is open and belongs to the repository.
   - Confirm the requested GitHub issue type exists.
   - Read the plan from the topic branch using `git show`, falling back to `gh api`.
   - Require the two supplied headings to occur exactly once.
   - Stop if any implementation-gating question lacks a concrete `Resolution:`.

2. **Inspect precedents and existing children**
   - Fetch each exemplar issue and imitate its structure and specificity.
   - Fetch existing sub-issues through GitHub’s REST API.
   - Avoid duplicate creation.

3. **Derive the backlog**
   - Find every direct subsection under the named implementation section.
   - Create a traceability map connecting each subsection to:
     - required files, APIs, and behavior;
     - relevant resolved research decisions;
     - spikes, screenshots, prototypes, and other artifacts;
     - tests and additional gating tests;
     - its preceding serial task.

4. **Draft all issues before changing GitHub**
   - Produce one issue per direct subsection, without merging or splitting tasks.
   - Include the topic branch and plan location prominently.
   - Require the future assignee to read the whole plan.
   - Name exact sections to reread rather than saying “relevant sections.”
   - State concrete resolution values and artifact paths.
   - Define implementation, tests, completion gates, and out-of-scope boundaries.
   - State that work must be assigned, completed, and merged serially.

5. **Create and link**
   - Write each body to a temporary file.
   - Create each issue through `gh api`, setting its issue type at creation.
   - Link it to the parent using the sub-issues REST endpoint.
   - Process them one at a time in plan order.
   - Retry linking three times, then stop on failure.
   - Leave every issue unassigned.

6. **Verify**
   - Check child count, one-to-one subsection coverage, ordering, type, open state, and absence of assignees.
   - Optionally add implementation progress checkboxes to the plan.

7. **Return the handoff**
   - An ordered table of created issues.
   - A comma-separated issue-number list suitable for `shepherd-task-given-list`.
   - A suggested downstream invocation using the repository and topic branch.

The four bundled examples are historical human prompts, not executable templates or sample generated issue bodies. They teach the model the desired campaign-specific detail level.

The important architectural boundary is: **the scripts deterministically collect inputs; Copilot interprets the skill and performs all plan analysis, issue drafting, GitHub mutation, and verification.**
