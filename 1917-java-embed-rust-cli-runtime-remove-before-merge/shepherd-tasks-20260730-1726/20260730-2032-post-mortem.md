## Section 7: Failure Analysis

### Primary failure: follow-up CCRA review did not arrive

The immediate failure signature is explicit: `Copilot’s follow-up review did not post within 10 minutes.` The POST to the requested-reviewers endpoint returned success, but after polling from the `2026-07-30T20:14:00Z` cutoff, only the original 20:12:04 UTC review remained visible. The requested-reviewers inspection showed team `copilot-sdk` and user `edburns`, not a visible Copilot reviewer entry.

### Contributing factors

1. **Asynchronous review latency exceeded a fixed timeout.** The script treated ten minutes without a new review as terminal even though fixes and CI were complete.
2. **Reviewer-request observability was ambiguous.** A successful API response did not prove that a new CCRA job had been queued.
3. **Semantic and process exit states diverged.** The phase-2 JSON result records `exitCode: 0` even though its final assistant message says `SHEPHERD FAILED`; the outer script correctly returned `1`. Consumers relying only on session result codes could misclassify this run.
4. **The first task was not reviewable by CCRA.** The 1,533-file restructure exceeded CCRA's 300-file limit, leaving CI and local gates as the only automated quality evidence for that PR.

### Recovery state

No logged code defect remains unresolved on [#2173](https://github.com/github/copilot-sdk/pull/2173): both known comments were fixed, both threads were resolved, focused tests passed, and CI passed. The remaining gate is a fresh CCRA confirmation review followed by merge.

## Section 8: Observations and Recommendations

### What worked

- Serial dependency ordering was enforced: [#2168](https://github.com/github/copilot-sdk/issues/2168) started only after [#2167](https://github.com/github/copilot-sdk/issues/2167) merged.
- Phase 1 produced strong, reproducible readiness evidence for both PRs.
- The local shepherd correctly diagnosed and fixed both substantive CCRA findings on [#2173](https://github.com/github/copilot-sdk/pull/2173).
- CI and review-thread gates prevented merging while confirmation remained uncertain.

### What failed

- A fixed 10-minute follow-up window converted review-service latency or queueing ambiguity into a campaign failure.
- The request operation lacked a durable review-run identifier or other positive queue acknowledgement.
- Session-level exit code reporting did not reflect the semantic failure.
- Large mechanical moves cannot receive normal CCRA coverage under the 300-file limit.

### Recommendations

1. Persist the review-request timestamp, target head SHA, and any returned request metadata; verify a queue signal before beginning the response timeout.
2. Make follow-up timeout configurable and retry the review request with bounded backoff when no Copilot reviewer or new review is observable.
3. On timeout after fixes and green CI, record a resumable state containing PR, head SHA, resolved thread IDs, and last review ID so a retry can continue without repeating completed work.
4. Propagate `SHEPHERD FAILED` to the CLI process exit code, or have the orchestration script parse a structured terminal status rather than infer success from the JSON result.
5. Detect the CCRA 300-file limit before requesting review and record an explicit `not reviewable` result instead of treating the response as a normal zero-comment round.
6. For large rename-heavy tasks, add an alternate review strategy that focuses on non-rename diffs and build/workflow changes while preserving the full CI gate.
