# Observing runtime execution identity

The SDK exposes identities observed on the runtime wire. Applications own the
association between their requests or Turns and runtime work; the SDK does not
infer that association or publish telemetry facts.

## Field sources and compatibility

These fields are available in SDK 1.0.14 with its default CLI 1.0.85. A configured
CLI path or external server can select a different runtime. Record both versions
and the connection/session lifetime when diagnosing an association; the SDK
version alone does not prove that a runtime emitted an optional field.

Use the accepted `Session::id()`, not a transformation of an application's
session URI. Hosts can remap URI paths or resolve collisions before creating SDK
sessions. Retain the application's full session identity separately.

The Rust payloads are generated by
[`scripts/codegen/rust.ts`](../../scripts/codegen/rust.ts) from the runtime's
`api.schema.json` and `session-events.schema.json`. Standalone SDK generation
uses the pinned CLI release schemas; runtime-checkout generation uses explicitly
selected same-checkout schemas. Change those contracts or their generators, not
the generated Rust files, when an additional runtime-owned field is required.

| Wire source | Rust access | Meaning |
| --- | --- | --- |
| `session.create` result `sessionId`; outer `session.event.params.sessionId` | `Session::id()`, `SessionEventNotification.session_id` | Runtime logical session and event routing context |
| `session.send` result `messageId` | `Session::send()`, `rpc::SendResult.message_id` | Accepted logical user message, not an event or loop iteration |
| `queue.pendingItems.items[].messageId?` | `rpc::QueuePendingItems.message_id` | Same logical message identity, when present |
| `queue.pendingItems.items[].id` | `rpc::QueuePendingItems.id` | Separate opaque queue-item key; batch rows share this key |
| `user.message.data.{messageId?,turnId?,interactionId?}` | `session_events::UserMessageData` | Message identity and the loop/interaction that consumed it, when observed |
| `assistant.turn_start.data.{turnId,interactionId?}` | `session_events::AssistantTurnStartData` | Agent-loop iteration and optional interaction |
| `assistant.message.data.{messageId,originatingMessageId?,turnId?,interactionId?}` | `session_events::AssistantMessageData` | Assistant-message identity, primary initiating message, and optional execution keys |
| `event.{id,parentId?,agentId?}` | `SessionEvent`, `TypedSessionEvent` | Event identity, chronological predecessor, and optional subagent identity |

Use `event.typed_data::<UserMessageData>()` and the corresponding generated
payload types for typed access. A malformed payload returns `None`; it must not
be replaced with a different event's identity. Unknown fields remain available
in the untyped event data. Do not forward that data wholesale into telemetry:
it includes message and tool content.

Optional fields remain absent on older runtimes. Empty strings are not usable
identities. The high-level Rust `send()` retains its legacy empty-string result
when an acknowledgement lacks `messageId`; consumers must treat it as missing.
The generated `SendResult` instead requires a string `messageId`. Neither
behavior licenses substituting an event ID or a locally generated ID.

## Distinguish a message, a loop iteration, and an interaction

An application Turn, including an AHP Turn, is a separate identity. AHP Turn IDs
are opaque and session-scoped; they are not required to be UUIDs and must never
be equated with runtime `turnId`.

Runtime `turnId` is a loop counter represented as a string. Counters can restart
across invocations. Interaction IDs can be reused for system-sourced work and
no-user HMAC sessions. Even `(sessionId, interactionId, turnId)` is not a
universally unique execution key.

The exact accepted `messageId` connects a send to `user.message.messageId`.
`assistant.message.originatingMessageId`, when present, identifies the primary
message that started the run, not the assistant message itself:

* Model/tool iterations and stop-hook corrections retain the primary origin.
* Immediate steering does not replace the active run's origin.
* For a batch starting a run, the last message ID is primary; earlier messages
  provide context. An empty batch has no initiating message.
* A subagent has its own initiating message. Its origin must not be substituted
  with the root agent's current message.

`user.message.delivery` distinguishes `idle`, `steering`, and `queued`;
`source` separately identifies origin. A queued acknowledgement means admission,
not consumption. Pending steering snapshots expose display text and counts, not
a supported per-message identity bridge. Never associate an arbitrary event with
the oldest pending send, queue position, or display text.

## Consume observations without inventing associations

1. Subscribe before create/resume using
   [PreparedSession](./streaming-events.md#subscribing-before-a-session-starts).
   Notifications can precede an RPC response. Drain concurrently or size the
   finite buffer; handle `Lagged` as missing evidence, not a successful outcome.
1. Retain the accepted message ID with the application's own request/Turn
   identity and session provenance. Allow either the acknowledgement or event
   to arrive first; only join matching observed keys.
1. Retain event and agent provenance when handling duplicates or late events.
   The SDK forwards duplicate notifications; it does not deduplicate or rewrite
   them. Deduplication of replayed evidence must not merge different sessions,
   executions, or conflicting payloads.
1. Resume/reconnect does not prove new execution, automatic replay, or identity
   continuity across a replaced runtime. Subscribe before resuming; request
   persisted history explicitly when needed. `eventLog.read` cursor expiry can
   produce overlap, and ephemeral events are not durable history. Keep the
   observation's connection/lifetime provenance separate from runtime IDs.
1. Keep incomplete associations incomplete. A returned send ID can be lost when
   its waiting future is cancelled after dispatch. Missing interaction, worker,
   or recovery keys are not supplied by the event's chronological `parentId`.

The root stream also contains subagent events marked by `agentId`. This marker
alone does not establish a worker's runtime session or its relationship to an
application Turn. A late worker event does not belong to whichever root Turn is
currently open. Likewise, `user.message.parentAgentTaskId` is a separate
runtime-provided task relationship, not an AHP parent or a replacement session ID.
Complete worker/recovery and product-telemetry joins require a verified
runtime-owned bridge; this interface does not promise one from an under-scoped
tuple.

## Content-free compatibility fixtures

[execution-identity-v1.json](../../rust/tests/fixtures/execution-identity-v1.json)
contains synthetic wire fragments, not a captured session or a prescribed event
order. `version` versions the fixture format; `sdkVersion` and `cliVersion`
identify its compatibility baseline. `sendResults` and `pendingItems` are RPC
result bodies; `notifications` contains complete `session.event` notifications.
These fixture metadata fields are not new runtime protocol fields.

The fragments deliberately include distinct message/event/queue identities,
repeated loop/interaction keys, another session, a worker, resume, and absent
legacy keys. Message/display content is empty and tool arguments are absent.
Consumers can replay permutations and duplicates to test their own association
logic without collecting prompts or tool output. SDK tests verify typed
round-tripping and delivery before/after acknowledgements, across interleaved
sessions, resume, and new connections. They do not establish deployed runtime
ordering, export coverage, or end-to-end telemetry joins.
